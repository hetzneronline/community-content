## Introduction

Feature flags allow you to change the behavior of an application while it is running. The application evaluates a flag at runtime and chooses a code path based on its value. The value itself is managed outside the application, so it can be changed without a new deployment or a restart.

Typical use cases are:

* **Kill switches** that turn off a faulty or expensive feature immediately.
* **Gradual rollouts** that enable a new feature for a subset of users first.
* **Graceful degradation**, where an application switches to a cheaper variant of a feature, for example under high load.

This tutorial shows you how to set up a simple feature flag service on your Hetzner server, define and change flag states, and how applications can evaluate flags, using two open source projects. [OpenFeature](https://openfeature.dev/) is a vendor-neutral specification and SDK for evaluating feature flags. [flagd](https://flagd.dev/) is a lightweight flag evaluation daemon that implements this specification and reads flag definitions from a file. Because the application only talks to the OpenFeature SDK, the flag backend can later be replaced without changing the evaluation code.


By the end of this tutorial, you will have:

* flagd running on your server and serving flags from a local file
* a flag definition file with a boolean flag and a flag with several variants
* a small Python web service that changes its behavior when you change a flag value

The setup is intended as a demonstration. Running flagd permanently using systemd, or securing it are practical next steps.

**Prerequisites**

* A Linux (64-bit) server
* Access to the root user or a user with sudo permissions
* Basic knowledge of the Linux command line and Python


## Step 1 - Install flagd

flagd can be installed using a single static binary or Docker. To install the binary, download the release archive, extract it, and install it to `/usr/local/bin`. This tutorial was tested with version 0.15.5. You can find newer releases on the [releases page](https://github.com/open-feature/flagd/releases).

```bash
wget https://github.com/open-feature/flagd/releases/download/flagd%2Fv0.15.5/flagd_0.15.5_Linux_x86_64.tar.gz
tar -xzf flagd_0.15.5_Linux_x86_64.tar.gz
sudo install -m 0755 flagd_linux_x86_64 /usr/local/bin/flagd
```

Check that the binary works:

```bash
flagd version
```

Install the tools used in the following steps:

```bash
sudo apt update
sudo apt install -y jq curl python3-venv
```

## Step 2 - Create a flag definition file

flagd reads flag definitions from a JSON or YAML file. Create a project directory, which will also hold the Python application later:

```bash
mkdir ~/flag-demo && cd ~/flag-demo
```

Create the file `flags.json`:

```bash
nano flags.json
```

Add the following content:

```json
{
  "$schema": "https://flagd.dev/schema/v0/flags.json",
  "flags": {
    "new-checkout": {
      "state": "ENABLED",
      "variants": {
        "on": true,
        "off": false
      },
      "defaultVariant": "off"
    },
    "response-quality": {
      "state": "ENABLED",
      "variants": {
        "high": "high",
        "medium": "medium",
        "low": "low"
      },
      "defaultVariant": "high"
    }
  }
}
```

Each flag consists of the following fields:

| Field            | Description |
| ---------------- | ----------- |
| `state`          | `ENABLED` or `DISABLED`. A disabled flag is treated as if it did not exist, and the application falls back to its own default value. |
| `variants`       | The possible values of the flag. The keys are names, the values can be booleans, strings, numbers, or objects. |
| `defaultVariant` | The variant that is returned when no targeting rule applies. |

The `$schema` entry is optional, but it enables validation and autocompletion in editors that support JSON Schema.

`new-checkout` is a simple on/off switch. `response-quality` has three variants and can be used to select between different implementations of the same feature, for example a full, a reduced, and a minimal variant of a response.

## Step 3 - Start flagd

In your first terminal, start flagd in the project directory:

```bash
cd ~/flag-demo
flagd start --port 8013 --uri file:./flags.json
```

`--uri file:./flags.json` tells flagd to read the flag definitions from the local file and to watch it for changes. flagd runs in the foreground and writes its log output to this terminal. Keep it open for the rest of the tutorial. You can stop flagd at any time with `Ctrl` + `C`.

By default, flagd uses the following ports:

| Port | Purpose |
| ---- | ------- |
| 8013 | Flag evaluation via HTTP and gRPC (used by the OpenFeature providers) |
| 8014 | Management (health checks and metrics) |
| 8015 | gRPC sync service (used by providers in in-process mode) |
| 8016 | OFREP, the OpenFeature Remote Evaluation Protocol |

The flagd evaluation API does not require authentication. Do not leave these ports reachable from the internet. Restricting access is described as next steps at the end of this tutorial.

## Step 4 - Evaluate flags with curl

flagd can be queried without any application code. Run the following commands in your second terminal.

Evaluate the boolean flag:

```bash
curl -s -X POST "http://localhost:8013/flagd.evaluation.v1.Service/ResolveBoolean" \
  -H "Content-Type: application/json" \
  -d '{"flagKey": "new-checkout", "context": {}}' | jq
```

Evaluate the string flag:

```bash
curl -s -X POST "http://localhost:8013/flagd.evaluation.v1.Service/ResolveString" \
  -H "Content-Type: application/json" \
  -d '{"flagKey": "response-quality", "context": {}}' | jq
```

The output should look similar to this:

```json
{
  "value": "high",
  "reason": "STATIC",
  "variant": "high"
}
```

`value` is the evaluated value, `variant` the name of the selected variant, and `reason` explains why this variant was selected. `STATIC` means that no targeting rule exists and the default variant was returned.

## Step 5 - Change a flag at runtime

flagd watches the flag file and applies changes to all following evaluations. No restart is required.

Open the flag file:

```bash
nano ~/flag-demo/flags.json
```

In the `response-quality` flag, change the default variant from `high` to `medium`:

```json
"defaultVariant": "medium"
```

Save the file and close the editor. In the flagd terminal, a log entry shows that the file change was detected. Evaluate the flag again:

```bash
curl -s -X POST "http://localhost:8013/flagd.evaluation.v1.Service/ResolveString" \
  -H "Content-Type: application/json" \
  -d '{"flagKey": "response-quality", "context": {}}' | jq .value
```

The output is now `"medium"`.

If flag values are changed by a program instead of by hand, the file should be replaced atomically, so that flagd never reads a partially written file. A common approach is to write to a temporary file in the same directory and then rename it, for example with `os.replace()` in Python.

## Step 6 - Evaluate flags in a Python application

In this step, you create a small web service that changes its response depending on `response-quality`. It uses the OpenFeature SDK with the flagd provider.

In your second terminal, create a virtual environment in the project directory and install the dependencies:

```bash
cd ~/flag-demo
python3 -m venv venv
source venv/bin/activate
pip install fastapi uvicorn openfeature-sdk openfeature-provider-flagd
```

Create the file `app.py`:

```python
import time

from fastapi import FastAPI
from openfeature import api
from openfeature.contrib.provider.flagd import FlagdProvider

# Simulated processing time per quality level in seconds.
# In a real application, each level would select a different code path.
QUALITY_LEVELS = {"high": 0.4, "medium": 0.2, "low": 0.1}
DEFAULT_QUALITY = "high"

api.set_provider(FlagdProvider(host="localhost", port=8013))
client = api.get_client("flag-demo")

app = FastAPI()


def resolve_quality():
    quality = client.get_string_value("response-quality", DEFAULT_QUALITY)
    if quality not in QUALITY_LEVELS:
        return DEFAULT_QUALITY
    return quality


@app.get("/report")
def report():
    quality = resolve_quality()
    time.sleep(QUALITY_LEVELS[quality])
    return {"quality": quality}
```

A few points about this code:

* `api.set_provider()` connects the OpenFeature SDK to flagd. To use a different flag backend later, only this line changes.
* The second argument of `get_string_value()` is the default value. If the evaluation failes, for example because flagd is not reachable, this value is returned instead of raising an exception. The application therefore keeps working with a defined behavior.
* `resolve_quality()` additionally checks that the returned value is one the application knows. A typo in the flag file then leads to the default behavior instead of an error.
* By default, the provider caches evaluated flags and receives change notifications from flagd over a stream. Flag changes therefore reach the application without polling.

Start the service in the second terminal:

```bash
uvicorn app:app --host 127.0.0.1 --port 8000
```

In your third terminal, send a request:

```bash
curl -s http://127.0.0.1:8000/report
```

Because you set the flag to `medium` in the previous step, the output is:

```json
{"quality":"medium"}
```

Open `~/flag-demo/flags.json` again, change the `defaultVariant` of `response-quality` to `low`, and save the file. Send the request again. The service now responds with `{"quality":"low"}` and answers faster, without having been restarted.

## Step 7 - Use targeting rules (Optional)

So far, every request received the same variant. Targeting rules select a variant based on an evaluation context, for example the subscription tier of a user. flagd uses [JsonLogic](https://flagd.dev/reference/flag-definitions/#targeting-rules) for these rules.

Open `~/flag-demo/flags.json`, set the `defaultVariant` of `response-quality` back to `high`, and add a `targeting` entry:

```json
"response-quality": {
  "state": "ENABLED",
  "variants": {
    "high": "high",
    "medium": "medium",
    "low": "low"
  },
  "defaultVariant": "high",
  "targeting": {
    "if": [
      { "==": [{ "var": "tier" }, "free"] },
      "low"
    ]
  }
}
```

Requests with `tier` set to `free` now receive `low`. All other requests receive the default variant `high`. Test it with curl:

```bash
curl -s -X POST "http://localhost:8013/flagd.evaluation.v1.Service/ResolveString" \
  -H "Content-Type: application/json" \
  -d '{"flagKey": "response-quality", "context": {"tier": "free"}}' | jq
```

The `reason` field now shows `TARGETING_MATCH`. In the Python application, the context is passed as an `EvaluationContext`:

```python
from openfeature.evaluation_context import EvaluationContext

context = EvaluationContext(attributes={"tier": "free"})
quality = client.get_string_value("response-quality", DEFAULT_QUALITY, context)
```

## Conclusion

You installed flagd, defined feature flags in a file, evaluated them with curl and from a Python application, and changed their values at runtime without restarting the application. The application only depends on the OpenFeature SDK, so the flag backend can be replaced later.

Flag values do not have to be changed by hand. Any process that can write the flag file, such as a monitoring script or a control loop, can switch applications between variants. This is how graceful degradation can be added to existing services without adding the decision logic to the services themselves.

**Next steps:**

To run flagd beyond a demonstration, consider the following steps:

* **Run flagd as a service:** Create a systemd unit so that flagd starts automatically and is restarted after failures. Run it under a dedicated system user instead of your own user or root.
* **Restrict network access:** Block the flagd ports from the internet and only allow the servers that need to evaluate flags.
* **Enable TLS:** If flags are evaluated over a network you do not control, use the `--server-cert-path` and `--server-key-path` options of `flagd start` and set `tls=True` in the provider.

To explore further features of flagd and OpenFeature:

* [In-process evaluation](https://flagd.dev/reference/providers/), where the provider evaluates flags locally and only synchronizes the definitions with flagd
* [Fractional evaluation](https://flagd.dev/reference/custom-operations/fractional-operation/) for percentage-based rollouts
* [Multiple flag sources](https://flagd.dev/concepts/syncs/), for example a file and an HTTP endpoint at the same time
* [Monitoring flagd](https://flagd.dev/reference/monitoring/) with Prometheus or OpenTelemetry
