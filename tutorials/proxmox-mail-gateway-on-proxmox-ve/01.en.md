## Introduction

[Proxmox Mail Gateway](https://github.com/proxmox/pmg-api) (PMG) is an open-source mail filtering gateway that sits between the internet and your mail server, filtering spam, viruses, and other threats before they ever reach an inbox. It can be deployed either as a second layer of defense in front of an existing filtering service, or as the primary, direct-facing mail gateway that receives internet mail itself. This tutorial covers the latter: PMG configured as the mail server your domain's MX record points to directly, with a separate internal mail server behind it handling mailboxes.

This tutorial covers installing PMG as a virtual machine on a Proxmox VE host running on a Hetzner dedicated server, then walking through the core mail proxy settings that make it actually route and protect mail correctly: relay domains, transports, trusted networks, TLS, and DKIM signing, followed by the spam and virus filtering engines.

By the end of this tutorial, you will have:

* A Proxmox Mail Gateway VM installed and running on Proxmox VE.
* Mail Proxy settings configured so PMG only relays for your domains and correctly forwards filtered mail to your real mail server.
* TLS and DKIM signing configured for outbound mail.
* Spam and virus filtering enabled.

**Prerequisites**

* A Hetzner dedicated server with Proxmox VE already installed - see [Install and Configure Proxmox VE](https://community.hetzner.com/tutorials/install-and-configure-proxmox_ve/) if you haven't set this up yet.
* An existing mail server (the one PMG will protect) reachable from the Proxmox VE host's network.
* A domain you control, with access to its DNS zone.
* Basic familiarity with Proxmox VE and mail server concepts (MX records, SMTP).

**Example terminology**

The `<...>` placeholders above are not real values - replace each one with your own domain, database name, and password before running any command.

* Domain: `<example.com>`
* PMG hostname: `mail-gateway.<example.com>`
* PMG's IP address: `<pmg_ip>` (used to reach the web interface before DNS is pointed at it)
* Internal mail server: `<mail_server_ip>` (the mail server PMG will forward filtered mail to)

## Step 1 - Download the PMG ISO

On the Proxmox VE host, download the ISO directly into local ISO storage. Check the [PMG downloads page](https://www.proxmox.com/en/downloads/proxmox-mail-gateway/iso) first to confirm the current version and adjust the filename below if a newer release is available:

```bash
cd /var/lib/vz/template/iso/
wget https://enterprise.proxmox.com/iso/proxmox-mail-gateway_9.1-1.iso
```

Verify the download against the SHA256 checksum published on the downloads page:

```bash
sha256sum proxmox-mail-gateway_9.1-1.iso
```

## Step 2 - Create the VM

PMG's official hardware requirements (recommended, for typical traffic) are a 64-bit multicore CPU, 4 GB RAM, and at least 8 GB of disk space. In practice, give it more disk than the bare minimum - the quarantine store grows over time, and you don't want to be resizing a disk under a production mail filter.

Create the VM from the Proxmox VE shell:

```bash
qm create 200 \
  --name mail-gateway \
  --memory 4096 \
  --cores 2 \
  --net0 virtio,bridge=vmbr0 \
  --scsihw virtio-scsi-pci \
  --scsi0 local-lvm:20 \
  --ide2 local:iso/proxmox-mail-gateway_9.1-1.iso,media=cdrom \
  --boot order=ide2 \
  --ostype l26
```

Adjust `200` (the VM ID), `local-lvm` (your storage), and the disk size to match your own environment. If you're using a different bridge or need a static MAC for a routed additional IP, adjust `--net0` accordingly - see the "Install and Configure Proxmox VE" tutorial linked in the prerequisites for details on network setup in a Hetzner environment.

Start the VM and open its console from the Proxmox VE web interface (**Datacenter → your node → 200 (mail-gateway) → Console**):

```bash
qm start 200
```

## Step 3 - Install PMG

The installer is largely the same Debian-based wizard used by Proxmox VE and Proxmox Backup Server:

1. Accept the license agreement.
2. Select the target disk (the VM's virtual disk - this will be wiped).
3. Choose your country, time zone, and keyboard layout.
4. Set a root password and administrator email address (this address doesn't need to work yet, but PMG uses it for local system notifications - you can change it later).
5. Configure the network: hostname (use an FQDN, for example `mail-gateway.<example.com>`), IP address, netmask, gateway, and DNS server. Since this is a VM rather than a cloud instance with automatic network provisioning, you need to enter these manually - use the same values you'd otherwise assign to this VM's network interface.
6. Review the summary and click **Install**.

The VM reboots into PMG once installation finishes. Remove the ISO from the CD-ROM drive so future reboots don't re-enter the installer:

```bash
qm set 200 --ide2 none
```

## Step 4 - First Login

Open `https://<pmg_ip>:8006` in your browser (note the port - it shares 8006 with Proxmox VE's own interface, but this is a separate machine) and log in as `root` with the password you set during installation. Your browser will warn about the self-signed certificate - this is expected and fine for now; if you plan to access this interface securely from outside your network later, PMG has a built-in ACME client under **Configuration → Certificates** that can issue a trusted Let's Encrypt certificate without needing to obtain one elsewhere.

You'll see a banner about the missing subscription - this is expected and doesn't affect functionality. PMG is fully open-source and usable without a subscription; the enterprise repository (and its faster-updated packages) is what a subscription unlocks. Don't run `apt update` yet - the enterprise repository is enabled by default and will fail without a subscription key, as covered in the next step.

## Step 5 - Switch to the No-Subscription Repository

If you don't have a Proxmox subscription, the default enterprise repository will return an authentication error on every `apt update` until you either add a subscription key or switch to the free no-subscription repository. For most Hetzner deployments without a Proxmox support contract, disable it:

```bash
echo "Enabled: false" >> /etc/apt/sources.list.d/pmg-enterprise.sources
```

Setting `Enabled: false` rather than deleting or commenting out the file matters for two reasons: commenting out individual lines in this newer `deb822` format can produce a "malformed entry" error instead of just disabling the source, and if you activate a subscription later, re-enabling access is as simple as removing this one line - no need to recreate the file from scratch.

Now add the no-subscription repository:

```bash
cat > /etc/apt/sources.list.d/proxmox.sources << 'EOF'
Types: deb
URIs: http://download.proxmox.com/debian/pmg
Suites: trixie
Components: pmg-no-subscription
Signed-By: /usr/share/keyrings/proxmox-archive-keyring.gpg
EOF
```

Note that this repository is served over plain HTTP rather than HTTPS - that's expected and documented behavior from Proxmox, not a mistake in this tutorial; the packages themselves are still cryptographically signed and verified via the `Signed-By` key regardless of the transport.

Update and upgrade the system:

```bash
apt update && apt dist-upgrade -y
```

If you do have a Proxmox subscription, skip the `Enabled: false` step above, and instead activate your subscription key under **Configuration → Subscription** in the web interface before running `apt update`.

## Step 6 - Configure Relaying

Go to **Configuration → Mail Proxy → Relaying**. The key setting here is **Default Relay**: the internal mail server that inbound mail for the domains you list in Relay Domains (Step 7) gets delivered to, once PMG has filtered it. If a single internal mail server handles all your Relay Domains, setting it here is usually simpler than defining every domain individually under Transports.

* **Default Relay**: `<mail_server_ip>` - your internal mail server's address.
* **Relay Port**: `25`
* **Relay Protocol**: `smtp`
* **Disable MX Lookup**: `No`
* **Smarthost**: leave empty, unless your hosting provider or ISP requires you to route PMG's own outbound connections (to the wider internet, not to your internal server) through their smarthost - some networks block direct outbound port 25 for anti-spam reasons. This is a separate concern from Default Relay above. When set, enter it as `<IP_address>:<port>` or `<FQDN>:<port>`, for example `smtp.provider.com:587` or `203.0.113.10:25`.

  One limitation worth knowing about: the GUI's Smarthost field has no place to enter a username or password. If your smarthost provider requires SMTP authentication (many do, especially on port 587), you need to configure Postfix SASL authentication manually on the command line, and persist it through PMG's [Service Configuration Templates](https://pmg.proxmox.com/pmg-docs/pmg-admin-guide.html#pmgconfig_template_engine) mechanism - anything you change directly in `/etc/postfix/main.cf` gets silently overwritten the next time PMG rewrites its configuration from the GUI.

  Install the SASL library PMG doesn't ship by default:

  ```bash
  apt update
  apt install libsasl2-modules -y
  ```

  Create a password map file with your smarthost's credentials, in the format `[host]:port username:password`:

  ```bash
  cd /etc/postfix
  touch relay_passwd
  chmod 0600 relay_passwd
  echo "[smtp.provider.com]:587 <username>:<password>" > relay_passwd
  postmap relay_passwd
  ```

  Rather than editing `/etc/postfix/main.cf` directly, copy PMG's own template to the override location and edit it there, so your changes survive the next GUI-triggered rewrite:

  ```bash
  cp /var/lib/pmg/templates/main.cf.in /etc/pmg/templates/main.cf.in
  ```

  Add the following lines to `/etc/pmg/templates/main.cf.in`:

  ```
  relayhost = [smtp.provider.com]:587
  smtp_sasl_auth_enable = yes
  smtp_sasl_password_maps = hash:/etc/postfix/relay_passwd
  smtp_sasl_security_options = noanonymous
  smtp_use_tls = yes
  ```

  Apply the template and restart Postfix:

  ```bash
  pmgconfig sync --restart 1
  ```

  Leave the Smarthost field in the GUI empty when doing this - having both set at once causes conflicting configuration. If you later upgrade PMG and this stops working, check whether the shipped `main.cf.in` changed upstream; PMG tracks overridden templates with `ucf` and will prompt you to review conflicts during a package upgrade, rather than silently discarding your changes.

  One more thing worth knowing: `/etc/postfix/relay_passwd` (and its hashed `.db` file) is a plain file PMG has no awareness of, so it's never touched by `pmgconfig sync` or package upgrades - but it's also not included in PMG's own backup tool (`pmgbackup`), which only covers `/etc/pmg/`, mail filter rules, and the statistics database. If you ever migrate this installation to a new server using PMG's built-in backup and restore, remember to copy `/etc/postfix/relay_passwd` (and re-run `postmap` on the target, or copy the `.db` file too) separately - it won't come across automatically.

If PMG sits in front of more than one internal mail server - for example, if you're using it as a shared gateway protecting several separate customers, each with their own mail server - Default Relay only covers the common case. Any Relay Domain whose mail needs to go somewhere other than Default Relay needs an explicit entry under **Transports** (Step 10), which takes priority over the default for that specific domain.

## Step 7 - Configure Relay Domains

Go to **Configuration → Mail Proxy → Relay Domains** and add every domain you want PMG to accept and relay mail for:

```
<example.com>
```

This is the setting that keeps PMG from becoming an open relay - PMG only accepts mail addressed to domains listed here. Any domain not listed is rejected during the SMTP conversation, before the message body is even transferred.

## Step 8 - Configure Ports

Go to **Configuration → Mail Proxy → Ports**:

* **External SMTP Port**: `25` - the port PMG listens on for mail arriving from the internet.
* **Internal SMTP Port**: `26` (default) - the port your internal mail server should use to hand its outbound mail to PMG for relaying.

Leave these at their defaults unless you have a specific conflict on this VM.

## Step 9 - Configure Options

Go to **Configuration → Mail Proxy → Options**. A few settings worth configuring deliberately here:

* **SMTP HELO Checks**: `Yes` - rejects connections whose HELO/EHLO greeting is missing, malformed, or not a fully-qualified hostname. Real mail servers always identify themselves properly here; spam software frequently doesn't bother. This setting matters specifically because PMG is the mail server that first receives the connection directly from the internet in this setup, rather than sitting behind another filtering layer that would have already screened out the worst offenders - PMG needs to do this screening itself.
* **Use SPF**: `Yes` - checks the connecting server's IP against the SPF record published in DNS for the claimed sender domain, and rejects mail where the sending IP isn't authorized to send for that domain. Like HELO checks, this only makes sense to enable when PMG is the server actually receiving the connection (so it sees the real originating IP) - if a gateway upstream of PMG were relaying mail to it, PMG would see that gateway's IP instead of the true sender, and SPF checks would compare the wrong address against the DNS record, either failing legitimate mail or letting through mail it shouldn't. Since this deployment has PMG accepting mail directly from the internet, that concern doesn't apply.
* **Reject Unknown Senders**: `Yes` - rejects mail whose sender domain has no valid DNS (no MX record and no A record) at all, meaning it can't possibly be a real, reachable domain. This is a soft check (a temporary 4xx rejection, so a legitimate sender with a brief DNS hiccup isn't permanently lost) that catches a meaningful share of spam from forged or entirely made-up sender domains, at a low false-positive cost.
* **Reject Unknown Clients**: generally leave this `No`, despite it sounding like a natural companion to the setting above. It rejects connections based on a strict reverse-DNS (PTR) check on the connecting IP, and this check runs before any whitelist exception can apply. In practice, a small but real percentage of otherwise-legitimate small mail servers have imperfect or missing rDNS configuration, and this setting has no escape hatch for them - you'd be turning away real mail with no way to selectively override it, for a check that catches proportionally less spam than the softer options above.
* **Hide Internal Hosts**: `Yes` - strips your internal mail server's hostname and IP out of the `Received` headers on outgoing mail. Without this, every message leaving your network reveals a piece of your internal network topology to whoever inspects the headers - not a critical vulnerability on its own, but unnecessary information disclosure with no real benefit to hand out.
* **SMTPD Banner**: customize this to something that doesn't reveal the mail server software or version, for example just your hostname. The default banner otherwise identifies enough for a scanner or attacker to fingerprint what's running before attempting anything else - minor hardening, but a cheap one.
* **Receiver Verification**: `Yes (550)` - PMG checks with your internal mail server that a recipient address actually exists before accepting the message. Without this, PMG accepts mail for addresses that don't exist and then has to bounce it after the fact, which is how servers end up sending "backscatter" spam to forged senders. The setting offers two reply codes to send back to the connecting sender when a recipient turns out not to exist:
  * `550` - a permanent rejection. The sender's mail server gets an immediate, definitive "no such user" and won't retry. This is the standard choice once you've confirmed verification is working correctly.
  * `450` - a temporary rejection. The sender's mail server queues the message and retries later. Useful briefly while first setting this up, since a misconfiguration on your internal mail server's side (for example, if it's slow to respond or briefly unreachable) causes a deferral instead of a hard, incorrect bounce of legitimate mail.

  Either way, this only works correctly if your internal mail server actually rejects unknown recipients itself - if it silently accepts mail for any address and generates its own bounce afterward, PMG's verification probe will report every address as valid, and this setting won't filter anything.
* **Greylisting**: consider enabling this if inbound spam volume is high. Here's how it actually works, per Proxmox's own documentation: the first time PMG sees mail from a given `<sender network, sender email, recipient email>` combination (referred to as a "triplet"), it temporarily rejects the message with a 450 code rather than accepting it. Legitimate mail servers treat this as a normal transient failure and retry automatically after a delay; most spam-sending software doesn't queue and retry at all, so a meaningful share of spam simply never comes back. Once a triplet successfully retries, PMG remembers it, and future mail matching that same triplet passes through immediately - so the delay only ever affects the *first* message from a new contact, not every message from them.

  The practical tradeoff is that first-contact delay, which the documentation describes as usually under 30 minutes, though in practice most legitimate mail servers retry within minutes. This occasionally surprises people expecting instant delivery from someone new. A useful escape hatch: mail from senders you explicitly trust (via the SMTP Welcomelist) skips greylisting entirely, so you're not stuck choosing between "greylisting everyone" and "greylisting no one." Skip enabling this altogether if the first-contact delay doesn't suit your use case.
* **DNSBL Sites**: a configurable list of DNS blocklist zones PMG queries against sender IPs and hostnames in mail bodies (SpamAssassin's DNSBL checks).

  **A note specific to Hetzner customers**: Spamhaus has [publicly stated](https://www.spamhaus.org/resource-hub/email-security/query-the-legacy-dnsbls-via-hetzner/) that Hetzner's network prevents them from attributing DNSBL queries to individual users, so since February 2025 they've been progressively blocking free public-mirror queries (plain `zen.spamhaus.org` and similar) from Hetzner IP ranges, returning an error code (`127.255.255.254`) instead of real results. If your mail server doesn't handle that error code correctly, this can result in mail being rejected outright rather than just silently skipping the check. The fix is to register for Spamhaus's free **Data Query Service (DQS)** instead of using the public mirror:

  1. [Sign up for a free DQS account](https://www.spamhaus.com/free-trial/sign-up-for-a-free-data-query-service-account/) and verify your email.
  2. Log in to the [Spamhaus portal](https://portal.spamhaus.com/) and copy your DQS key.
  3. Use the key-prefixed zone names instead of the public mirror equivalents, for example:
     * `<your_dqs_key>.zen.dq.spamhaus.net` (replaces `zen.spamhaus.org`)
     * `<your_dqs_key>.dbl.dq.spamhaus.net` (domain blocklist)
     * `<your_dqs_key>.zrd.dq.spamhaus.net` (zero-reputation domains - flags very recently registered domains, which are disproportionately used for spam and phishing)

  Combine this with a couple of free, registration-free zones as well - `bl.mailspike.net` and `psbl.surriel.com` are both still active and don't require signing up for anything:

  ```
  <your_dqs_key>.zen.dq.spamhaus.net
  <your_dqs_key>.dbl.dq.spamhaus.net
  <your_dqs_key>.zrd.dq.spamhaus.net
  bl.mailspike.net
  psbl.surriel.com
  ```

  Adding more zones isn't automatically better - several forum threads from long-time PMG admins note that stacking in less-maintained or inconsistent lists mostly adds false positives rather than catching more spam. Add zones deliberately, one at a time, watching for false positives before adding the next.

  One thing worth knowing before you rely on this: several DNSBL providers rate-limit queries **per public IP address**, and if your PMG VM resolves DNS through your ISP's nameserver or a public resolver like `8.8.8.8` or `1.1.1.1`, you're sharing that quota with everyone else using the same resolver - meaning DNSBL lookups can silently start failing under load, showing up in mail logs or SpamAssassin hits as `URIBL_BLOCKED`, `RCVD_IN_DNSWL_BLOCKED`, or `SURBL_BLOCKED`. Proxmox's own documentation recommends running a local recursive resolver (they use [Unbound](https://pmg.proxmox.com/wiki/DNS_server_on_Proxmox_Mail_Gateway)) directly on the PMG VM so its DNSBL queries go out under your own dedicated public IP instead of a shared one:

  ```bash
  apt install unbound dnsutils
  dig a proxmox.com @127.0.0.1 +short
  ```

  The `dig` command here is a quick sanity check, not part of the actual configuration - it asks the resolver you just installed (`@127.0.0.1`) to look up `proxmox.com`'s IP address itself. Getting back an IP address, rather than a timeout or error, confirms Unbound is listening and resolving correctly before you point PMG at it.

  Then point PMG's own DNS resolution at it, either via **Configuration → Network/Time → DNS** in the web interface (set DNS Server 1 to `127.0.0.1`) or by editing `/etc/resolv.conf` directly, and restart the mail services so the change takes effect:

  ```bash
  systemctl restart pmg-smtp-filter pmgpolicy postfix
  ```

  See the linked wiki page for more advanced setups, such as forwarding your own internal domain's lookups to an internal DNS server while still resolving DNSBL zones recursively.

  One important distinction: running your own Unbound resolver solves the *shared-quota* problem above, but it does **not** solve the Hetzner-specific Spamhaus block described earlier - that block is based on which network your queries originate from, and a resolver running on the same Hetzner VM still queries from a Hetzner IP either way. The only fix for that specific issue is switching to the DQS key-based zones.

## Step 10 - Configure Transports

Go to **Configuration → Mail Proxy → Transports**. Use this when a specific Relay Domain needs to go to a different internal mail server than the one set as Default Relay in Step 6 - this is exactly the case when PMG is a shared gateway in front of several separate mail servers rather than a single one:

* **Relay Domain**: `<example.com>`
* **Host**: `<mail_server_ip>` (this domain's specific mail server - different from Default Relay)
* **Protocol**: `smtp` (or `lmtp` if that domain's mail server expects LMTP - if so, note that **Use MX** becomes irrelevant and is disabled automatically)
* **Port**: the port that mail server listens on for incoming relayed mail (often `25`, sometimes a dedicated submission port depending on that server's own configuration)
* **Use MX**: `No` - you're pointing directly at a specific host, not looking up its MX records

Add one entry per domain that needs to diverge from Default Relay. Domains not listed here simply fall through to whatever you set as Default Relay in Step 6.

## Step 11 - Configure Networks

Go to **Configuration → Mail Proxy → Networks** and add your internal mail server's IP (or the network it's on) as a trusted network:

```
<mail_server_ip>/32
```

Hosts listed here are allowed to relay outbound mail through PMG. Without this, your internal mail server's own outbound mail (the mail *it* sends, as opposed to mail PMG delivers *to* it) has nowhere authorized to go through PMG's proxy. If you configured multiple internal mail servers under Transports in Step 10, add each of their IPs here individually - each one needs to be explicitly trusted, not just the one set as Default Relay.

## Step 12 - Configure TLS

Go to **Configuration → Mail Proxy → TLS**:

* **Enable TLS**: `Yes`
* **Enable TLS Logging**: `Yes` - useful for troubleshooting delivery issues later without having to turn logging on retroactively.
* **Add TLS received header**: `Yes`

When you enable TLS, PMG generates a self-signed certificate automatically for encrypting SMTP sessions (`/etc/pmg/pmg-tls.pem`) - this is separate from the web interface's own certificate, and generally doesn't need replacing, since mail servers negotiating opportunistic TLS don't validate the certificate chain the way a browser does.

If you have specific partner domains that should only ever be reached over TLS (never falling back to plaintext), add a **TLS Destination Policy** entry for that domain.

## Step 13 - Configure DKIM

Go to **Configuration → Mail Proxy → DKIM**:

* **Enable DKIM Signing**: `Yes`
* **Selector**: `default` (or any short identifier of your choosing - this becomes part of the DNS record name later)
* **Sign Domains**: `<example.com>`
* **Sign all Outgoing Mail**: `Yes` - signing everything is simpler to reason about and maintain than trying to select which specific mail needs signing.

Saving this generates a DKIM key pair. You'll need the public key for a DNS record in Step 16 - the admin interface shows it directly on this page once signing is enabled.

## Step 14 - Configure the Spam Detector Engine

Go to **Configuration → Spam Detector → Options**. This page configures the SpamAssassin engine itself - which detection techniques it uses and how - rather than what PMG actually *does* with a given spam score (that part lives in **Mail Filter → Rules**, covered separately, since it's a rule-based system rather than a single threshold setting).

* **Use auto-welcomelists**: `Yes` - enables SpamAssassin's Auto-Welcomelist plugin, which adjusts a message's score based on the historical reputation of that specific sender/IP combination with your system. A sender you've received legitimate mail from repeatedly gets a small trust bonus over time.
* **Use Bayesian filter**: `Yes` - a statistical classifier that learns from mail your system has already seen, improving accuracy over time based on what's been marked spam versus legitimate in your environment.
* **Use RBL checks**: `Yes` - enables SpamAssassin's own real-time blocklist lookups as part of content scoring. This is a separate mechanism from the DNSBL Sites you configured under Mail Proxy in Step 9: that one rejects mail outright at the SMTP level before it's even queued, while this one contributes to the overall spam score during content analysis. Both are worth having enabled; they catch overlapping but not identical things.
* **Use Razor2 checks**: `Yes` - enables Vipul's Razor2, a collaborative database of spam fingerprints. Two things worth knowing before you rely on this: first, Razor2 needs a one-time registration before it works at all -

  ```bash
  razor-admin -create
  razor-admin -register
  ```

  Second, its default scoring weight is quite low out of the box. If you want Razor2 hits to meaningfully affect filtering, increase `RAZOR2_CF_RANGE_51_100` and `RAZOR2_CHECK` under **Configuration → Spam Detector → Custom Scores** (a score of `8` is a reasonable starting point used by other admins), then click **Apply Scores**.
* **Extract Text from Attachments**: `No` is the default, and reasonable to leave as-is unless you have a specific reason to change it. Enabling this extracts and scans text from attached doc, pdf, rtf, and image files for spam content - useful for catching spam hidden inside attachments, but meaningfully more CPU-intensive per message.
* **Max Spam Size (bytes)**: `262144` (256 KB) by default - the maximum message size that gets full content analysis. Messages larger than this skip content scanning (though they're still subject to the SMTP-level checks from Step 9), since scanning very large messages in full is expensive for comparatively little anti-spam benefit - spam is rarely large.
* **Languages**: `all` by default. Restricting this to specific language codes tells SpamAssassin which languages are expected for legitimate mail, which factors into scoring - only worth narrowing if you're confident you'll never legitimately receive mail in other languages.
* **Backscatter Score**: `0` by default, meaning it's effectively off. Backscatter is what happens when someone forges your domain as the sender of spam, and the (unwitting) receiving servers bounce that mail back - to you, since you appear to be the sender. If you want PMG to specifically score these bounce-notification patterns higher, this needs a non-zero value; some admins pair this with a `whitelist_bounce_relays` entry for their own legitimate outbound relays first, so real bounces of mail you actually sent aren't caught by the same net.
* **Heuristic Score**: `3` by default - this feeds in scoring from ClamAV's heuristic detections (encrypted archives or documents, and scanned phishing URLs) into the overall spam score, bridging a virus-engine signal into spam scoring rather than keeping the two entirely separate.

To actually act on the resulting spam score (tag the subject, quarantine, or block outright at a given threshold), create rules under **Mail Filter → Rules** using **Spam Level** as the matching condition - this is outside the scope of this tutorial's installation focus, but worth knowing before you assume spam filtering is fully configured just from this page.

## Step 15 - Configure the Virus Detector

Go to **Configuration → Virus Detector → Options**. PMG scans mail with ClamAV. The fields on this Options tab are mostly about how deeply archives get inspected and what counts as suspicious on its own:

* **Block encrypted archives and documents**: `Yes` - ClamAV can't look inside an encrypted archive or document to scan its actual contents, so this setting treats the encryption itself as a red flag and blocks the file rather than silently letting an unscannable payload through. Legitimate encrypted files do exist, but malware is frequently password-protected specifically to evade AV scanning, so this is a reasonable default rather than an overly aggressive one.
* **Max recursion**: `5` - how many levels deep PMG will unpack nested archives (a zip inside a zip inside a zip, and so on) before it stops. This exists as zip-bomb protection - without a limit, a maliciously crafted, deeply nested archive could consume enormous CPU and memory trying to fully unpack.
* **Max files**: `1000` - the maximum number of files PMG will extract from a single archive to scan. Same purpose as Max recursion: bounding resource usage against archives crafted to contain an excessive number of files.
* **Max file size**: `25000000` (25 MB) - individual files within an archive larger than this are skipped rather than scanned. Combined with Max scan size below, this keeps a single oversized attachment from tying up the scanner disproportionately.
* **Max scan size**: `100000000` (100 MB) - the total amount of data scanned per input file overall, across everything unpacked from it. This is the aggregate cap; Max file size limits any one file within an archive, while this limits the sum total.
* **Max credit card numbers**: `0` (disabled) by default. This isn't a virus detection setting at all - it's a basic data-loss-prevention check that flags a message if it contains at least this many credit card or social security number patterns, useful for catching, for example, someone accidentally emailing a spreadsheet full of customer card numbers. Leave it at `0` unless you specifically want this kind of outbound content scanning; a low nonzero value (like `1` or `2`) enables it.

As with spam, what happens to a message ClamAV flags as infected (quarantine versus outright block) is defined through a rule in **Mail Filter → Rules** with a **Virus** match condition, not on this page. A sensible default if you haven't set one up yet is to block infected mail outright rather than quarantine it - a quarantined virus is still a virus sitting on disk that someone might eventually click into.

### Extending ClamAV with Third-Party Signature Feeds (Optional)

ClamAV's own official signatures (`main.cvd`/`daily.cld`, updated via `database.clamav.net`) are general-purpose. Several community and vendor-maintained feeds add signatures focused specifically on things that show up disproportionately in email - phishing, malicious macros, malware hidden in archives - and can meaningfully improve detection beyond the defaults. Well-known ones include [R-fx Networks (rfxn)](https://rfxn.com/), [Sanesecurity](https://sanesecurity.com/), and [InterServer](https://sigs.interserver.net/), among others.

Adding one is done the same way as the SASL configuration in Step 6: since `freshclam.conf` is also managed by PMG's config engine and gets rewritten on sync, edit it through the template override rather than directly:

```bash
cp /var/lib/pmg/templates/freshclam.conf.in /etc/pmg/templates/freshclam.conf.in
```

Add one or more `DatabaseCustomURL` lines to the end of `/etc/pmg/templates/freshclam.conf.in`, for example:

```
DatabaseCustomURL https://rfxn.com/downloads/rfxn.ndb
DatabaseCustomURL https://rfxn.com/downloads/rfxn.hdb
```

Apply the change and trigger an update:

```bash
pmgconfig sync --restart 1
```

Rather than listing every available signature file here, Sanesecurity publishes a [reference table](https://sanesecurity.com/usage/signatures/) of each database they (and several affiliated projects) produce, what it targets, and its approximate false-positive risk - use that to pick the specific feeds that make sense for your mail volume and risk tolerance, rather than adding everything at once. That table lists database *names* (for example `junk.ndb`), not full download URLs - you build the actual `DatabaseCustomURL` by combining a mirror's base address with the name, for example `https://mirror.rollernet.us/sanesecurity/junk.ndb`. If you'd rather see a set of already-complete URLs as a starting point, the [Gentoo wiki's ClamAV Unofficial Signatures page](https://wiki.gentoo.org/wiki/ClamAV_Unofficial_Signatures) lists several worked examples in exactly that format. A couple of things worth knowing before relying on any of these: they're unofficial and unaffiliated with the ClamAV project itself, so check each provider's own usage terms before adding it; and since most are distributed through community mirrors rather than a single canonical source, an individual mirror can occasionally go down or move - keep an eye on `freshclam`'s update logs if detection quality seems to quietly regress over time.

## Step 16 - Update DNS Records

Once mail routing works, update your domain's DNS zone:

* **MX**: point `<example.com>`'s MX record at `mail-gateway.<example.com>`, replacing (or standing alongside, at a lower priority during testing) whatever it previously pointed to.
* **SPF**: update your SPF TXT record to include PMG's public IP, so receiving servers know mail from PMG is authorized to send on your domain's behalf.
* **DKIM**: add the TXT record for the selector you chose in Step 13, in the form `<selector>._domainkey.<example.com>`, with the public key value PMG generated.
* **DMARC**: if you don't already have a DMARC record, this is a good point to add one, now that SPF and DKIM are both in place.

## Step 17 - Validate

* [ ] Sending a test message from an external address to a mailbox on `<example.com>` arrives, and shows PMG's hostname in the `Received` headers.
* [ ] Sending a test message from a mailbox on `<example.com>` to an external address arrives, and the external side shows a valid DKIM signature (many providers, including Gmail, show this under "message details" or similar).
* [ ] Attempting to relay mail through PMG for a domain **not** in Relay Domains is rejected.
* [ ] Connecting to PMG's SMTP port manually (for example with `telnet <pmg_ip> 25`) and issuing a malformed `HELO` is rejected, confirming the Options-tab checks from Step 9 took effect.
* [ ] `Mail Proxy → TLS` shows active sessions using TLS for at least some connections (visible in the mail log/tracking center after some traffic has passed through).

## Conclusion

You now have Proxmox Mail Gateway running as a VM on Proxmox VE, filtering mail for your domain before it reaches your real mail server, with TLS and DKIM signing configured for outbound mail. From here, the natural next step is building out rules under **Mail Filter → Rules** to actually act on spam and virus scores, and reviewing the quarantine periodically to tune false positives.
