## Introduction

A newly deployed Linux server should not expose more network services than necessary. A simple host-level firewall can reduce the number of reachable services, while Fail2ban can help protect services such as SSH from repeated authentication attempts.

In this tutorial, you will configure UFW and Fail2ban on an Ubuntu server running on Hetzner Cloud. You will first verify SSH access, configure the firewall, install Fail2ban, enable its SSH jail, and then verify the resulting configuration.

The examples use the standard placeholder values from the Hetzner tutorial format. Replace them with values appropriate for your own server.

**Prerequisites**

* A Hetzner Cloud server running Ubuntu
* SSH access to the server
* Basic Linux command-line knowledge
* An SSH session that you can keep open while changing firewall rules

Do not use an actual public IP address in this tutorial. Use the example addresses provided by the Hetzner tutorial template.

## Step 1 - Update the Server

Start by connecting to the server and updating the package information.

```bash
sudo apt update
sudo apt upgrade
```

Check the installed Ubuntu version:

```bash
cat /etc/os-release
```

You should see the Ubuntu release information.

Keeping the system updated before configuring security software reduces the chance of troubleshooting an outdated package or service.

## Step 2 - Verify SSH Access

Before enabling the firewall, make sure you can connect to the server over SSH.

For example:

```bash
ssh holu@<203.0.113.1>
```

Keep your current SSH session open while configuring UFW.

This is important because an incorrect firewall rule can prevent new SSH connections. An existing SSH session gives you an opportunity to correct the configuration without immediately losing access.

## Step 3 - Install and Configure UFW

Install UFW:

```bash
sudo apt install ufw
```

Check its current status:

```bash
sudo ufw status verbose
```

Before enabling UFW, explicitly allow SSH:

```bash
sudo ufw allow OpenSSH
```

Check the rule:

```bash
sudo ufw status numbered
```

You should see an SSH rule.

Now enable UFW:

```bash
sudo ufw enable
```

Check the firewall again:

```bash
sudo ufw status verbose
```

### Set the Default Policies

For a typical server, incoming connections can be denied by default while outgoing connections remain allowed:

```bash
sudo ufw default deny incoming
sudo ufw default allow outgoing
```

Make sure SSH is still allowed:

```bash
sudo ufw allow OpenSSH
```

If the server hosts a website, allow HTTP and HTTPS:

```bash
sudo ufw allow 80/tcp
sudo ufw allow 443/tcp
```

Review the complete configuration:

```bash
sudo ufw status numbered
```

Only open ports that are actually required by services running on the server.

## Step 4 - Check Listening Services

Firewall rules should be based on the services that the server actually needs to expose.

List listening TCP and UDP sockets:

```bash
sudo ss -lntup
```

Review the output and identify services listening on public interfaces.

For example, a web server might listen on ports 80 and 443, while SSH normally listens on port 22.

Do not open a firewall port simply because an application might use it. First verify that the service is installed, running, and actually listening.

## Step 5 - Install Fail2ban

Install Fail2ban:

```bash
sudo apt install fail2ban
```

Enable and start the service:

```bash
sudo systemctl enable --now fail2ban
```

Check its status:

```bash
sudo systemctl status fail2ban
```

You can also verify that the Fail2ban server is responding:

```bash
sudo fail2ban-client ping
```

A working installation should return:

```text
Server replied: pong
```

## Step 6 - Configure the SSH Jail

Avoid modifying the package-provided `jail.conf` directly. Create a local configuration file instead:

```bash
sudo nano /etc/fail2ban/jail.local
```

Add:

```ini
[DEFAULT]
bantime = 1h
findtime = 10m
maxretry = 5
backend = systemd

[sshd]
enabled = true
```

Save the file and restart Fail2ban:

```bash
sudo systemctl restart fail2ban
```

Check the service:

```bash
sudo systemctl is-active fail2ban
```

The expected result is:

```text
active
```

## Step 7 - Verify the SSH Jail

List the configured jails:

```bash
sudo fail2ban-client status
```

Then check the SSH jail:

```bash
sudo fail2ban-client status sshd
```

The output contains information about the jail, including the number of currently banned addresses and authentication failures.

Do not deliberately generate authentication attacks just to test the ban mechanism on a production server. Configuration and service status checks are safer ways to verify the setup.

## Step 8 - Validate the Configuration and Logs

Test the Fail2ban configuration:

```bash
sudo fail2ban-client -t
```

Check recent Fail2ban messages:

```bash
sudo journalctl -u fail2ban --since "30 minutes ago"
```

These logs are useful when diagnosing configuration problems or determining whether a jail started successfully.

If Fail2ban fails to start, inspect the journal before changing the configuration:

```bash
sudo systemctl status fail2ban
sudo journalctl -u fail2ban -n 50 --no-pager
```

## Step 9 - Perform a Final Security Check

Review the firewall:

```bash
sudo ufw status verbose
```

Review numbered rules:

```bash
sudo ufw status numbered
```

Review listening services:

```bash
sudo ss -lntup
```

Check for failed system services:

```bash
sudo systemctl --failed
```

Finally, verify Fail2ban:

```bash
sudo fail2ban-client ping
sudo fail2ban-client status
sudo fail2ban-client status sshd
```

At this point you should have:

* UFW enabled
* SSH explicitly allowed
* Only required application ports exposed
* Fail2ban running
* The SSH jail enabled
* A way to inspect firewall and Fail2ban status

## Step 10 - Recover From an Incorrect Firewall Rule

If you accidentally add an incorrect UFW rule, first inspect the numbered rules:

```bash
sudo ufw status numbered
```

Remove the incorrect rule using its number:

```bash
sudo ufw delete <rule-number>
```

If SSH access was accidentally removed, restore it:

```bash
sudo ufw allow OpenSSH
```

Then verify:

```bash
sudo ufw status verbose
```

When making firewall changes remotely, keeping an existing administrative SSH session open is a simple precaution against accidental lockout.

## Common Mistakes

### Enabling UFW before allowing SSH

Always allow the SSH service before enabling the firewall on a remotely managed server.

### Closing the only SSH session

Keep an existing SSH connection open until you have verified that the new firewall rules work.

### Opening unnecessary ports

Check actual listening services with:

```bash
sudo ss -lntup
```

Only expose ports required by the server workload.

### Editing the main Fail2ban configuration

Use `/etc/fail2ban/jail.local` for local configuration rather than modifying the package-provided configuration directly.

### Assuming Fail2ban replaces a firewall

UFW and Fail2ban solve different problems. UFW controls network access, while Fail2ban can react to repeated authentication failures.

### Not checking logs

When something does not behave as expected, check:

```bash
sudo journalctl -u fail2ban
```

and:

```bash
sudo ufw status verbose
```

before making additional changes.

## Conclusion

You have configured a basic host-level security layer for an Ubuntu server.

UFW provides the firewall policy, while Fail2ban monitors authentication-related activity and can temporarily block sources that repeatedly fail authentication.

The configuration should be reviewed whenever services are added or removed from the server. Regularly checking firewall rules, listening services, Fail2ban status, and system logs helps keep the configuration aligned with the actual workload.

**Next steps:**

* Review the services listening on the server.
* Remove firewall rules that are no longer required.
* Keep Ubuntu and installed security packages updated.
* Monitor authentication and system logs regularly.
